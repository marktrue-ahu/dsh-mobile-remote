# 分支图分页采用 tip 绑定的短期快照

Status: accepted

多分支提交图不能把移动端已加载列表当作完整拓扑，也不能在分页期间随引用变化而悄悄换到另一段历史。分支图首次请求因此以经过授权仓库内的“引用名称 + tip OID”选择集建立短期快照，后续请求使用绑定该选择集、仓库、排序语义和 TTL 的不透明排他游标；引用或上下文变化时返回 `graph-stale`，由用户显式刷新。快照只需固定查询身份和边界，不要求保存完整提交列表，从而在拓扑一致性、服务端资源和大仓库分页之间取得平衡。

## 补充（2026-11-12，issue #86）

快照与 HTTP 传输方式无关：POST 首屏创建的 `snapshotId` 可用 GET 续页，GET 首屏也可用 POST 续页；`cursor` 与 tip 绑定、TTL 语义不变。选择集从 5 扩展为 5/10/不限（服务端 POST 最多 128），tip 数量会增加 `git log` 并集与深分页成本，仍由同一 25s deadline、snapshot TTL 与分页上限约束。

## Consequences

- provider 必须验证引用名称确实解析到请求中的 tip OID，并返回所有选中 tip 可达提交的去重并集；不得接受任意 OID、静默跟随移动后的引用或回退到 `--all`。
- 快照有效时，多页拼接必须无重复、无遗漏；无法验证快照、游标、仓库或引用仍一致时，宁可失效并刷新，也不混合两次查询结果。
- App 收到仓库变化事件时保留当前图并提示刷新；新增或替换筛选分支会创建新快照，不与旧快照分页混用。
- provider 可以保存轻量快照绑定并按不可变 tip 重新查询，无需把完整提交图常驻内存；TTL、页大小和输出上限仍由服务端控制。

# 0015 子代理列表按创建时间倒序，状态取自 store 而非 REST activity

状态：已接受

「会话工具 → 子代理」页签此前不排序、也不显示运行状态。本次让列表按**创建时间由近到远**排列，并使每个子代理的会话运行状态可见。背景与验收见 GitLab `ahedu/dsh-mobile-remote#17`。

**排序键与会话列表有意不同**。会话列表按 `lastMessageAt`（"最近聊了什么"）；子代理列表按 `createdAt`（"我最近派了什么"）。两者若统一用 `lastMessageAt`，子代理一干活就会跳到列表最前，顺序随活动不断抖动；而用户在这个列表里找的是"我刚派出去的那个"。因此这里接受"同一产品内两处时间排序语义不一致"的代价，避免为了一致而牺牲稳定性。运行中的子代理**不置顶**，理由相同。

**状态真源是 store，不是 RPC 返回值**。`/m/api/subagents` 的 `status` 是内核 `activity`，而休眠/归档父会话走持久化分支时它恒为 `inactive`。若 UI 用它，会出现"文本说 inactive、实际在跑"的自相矛盾。客户端改为复用会话列表同一套判定（`agent/status` 帧 + `session/jobs` 帧合成的 `rowStateOf`），REST 只提供列表与标题——子代理本身就是会话，其状态数据链路本就按 sessionId 就绪，无需新增端点。视觉上复用会话列表的方形虚线指示器，因此不存在第二套运行状态语义。

**不呈现「等待用户处理」**。子代理的审批策略被内核钉死为 `never`，审批态永不会出现；问询虽在机制上可达，但按领域规则（`CONTEXT.md`「子代理不向用户提问」）子代理不应直接向用户提问，需要用户决定的事应由主会话提出。因此该状态是主会话列表的概念，子代理列表不呈现它。这是**有意的不做**：若将来真的出现子代理提问导致的静默挂起，应作为一个独立问题从工具层解决，而不是在这里补一个状态指示。

## Consequences

- 依赖 `createdAt` 必须由插件透出：内核 `SubagentListEntry` 只用于排序、不外露该字段，两处裁剪都要新增它，并显式统一排序方向（内核活跃分支升序、持久化分支降序，此前两条路径顺序相反）。
- `SessionIcon` 增加 `icon` / `squircle` 覆盖，使子代理行能共享同一份虚线/颜色/动效契约，而不是复制一份绘制逻辑。
- 状态随 SSE 实时变化，列表顺序不受影响——顺序只在重新加载时按 `createdAt` 决定。

## 已知限制（有意不修，勿当缺陷重复排查）

活跃父会话分支从内核内存注册表取 `createdAt`（`sessions.get(id).header.createdAt`），取不到就省略该字段，**不做持久化 header 回退**。后果：活跃父会话下，已结束的子代理会缺 `createdAt` → 排序时被排到最后、也不显示时间；休眠父会话不受影响（走持久化 header，全覆盖）。真机实测（2026-09-30）确认该现象存在且用户接受，因此**有意保留**：缺字段有明确且稳定的回退行为（排最后），不影响主路径，而修它需要为「已结束子代理」再引入一次持久化读取。

若将来要修，方向是活跃分支取不到内存 header 时回退到持久化 header——`/m/api/sessions` 对同一 id 确实带 `createdAt`，证明数据源存在。

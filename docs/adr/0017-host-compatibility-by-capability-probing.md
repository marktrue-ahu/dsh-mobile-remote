# 0017 宿主兼容：按能力探测与显式报告，而非版本门禁

状态：已接受。背景与验收见 GitLab `ahedu/dsh-mobile-remote#19`。

插件对宿主（DSH 内核）的兼容**不设版本门禁**：不按宿主版本号拒绝启动，也不维护"受支持的宿主版本区间"。改为在运行期**探测**宿主提供了哪些服务与接口，按代际走不同代码路径，并把每一项能力的真实状态**显式报告**出去。

同时把包依赖范围的上界去掉（四包统一为 `>=0.1.0-rc.6`），使 0.2.x 及以后不再被包管理器挡住。

## 为什么不是版本门禁

**宿主不为它的 API 声明契约版本**。这一点与 Git 能力接缝形成鲜明对照：那里提供者声明 `contractVersion`，消费者要求**完全一致**才算兼容（见 `CONTEXT.md` 的「兼容版本」），是一套声明式校验。宿主侧没有对应机制，插件除了探测别无选择——写死一个版本区间只是在猜。

**门禁会挡住本可以不挡的用户**。`0.1.5` → `0.2.0` 的迁移里，插件调用的 18 个宿主服务中**只有 4 处**真正不兼容，其余要么逐字节相同、要么纯增量（`credentials`、`messageFeedback`、`webServer`、`sessions`、`agents`、`llm` 的类型声明在两代间甚至完全一致）。为了 4 处差异把所有新版本用户挡在门外，代价与收益不成比例。

## 为什么"显式报告"是这套决策的前提而非附加项

不设门禁意味着**兼容性只能靠探测保证**——而探测本身已被证明不完备。本次四处不兼容**全部表现为静默失败**：

| 变更 | 静默失败的样子 |
|---|---|
| 任务查询/终止的身份从会话对象改为会话 id 字符串 | `list()` 返回空数组，看起来像"这个会话确实没有任务" |
| 任务事件订阅改为统一事件流 | 旧回调变成 no-op，实时推送悄悄退化成轮询 |
| 设置读取从 `get()` 改为 `describe()` | 抛出的类型错误被 try/catch 吞掉，配置页字段凭空消失 |
| 事件流打开的位置参数移位（取消信号从第 3 位到第 5 位） | 传错位不报参数错误，而是在宿主内部 `AbortSignal.any` 处抛异常、被重试循环吞掉，最终表现为"该通道不可用" |

四处**没有一处抛到用户面前**。类型系统拦不住（第四处就是纯粹的位置参数错位），服务存在性探测也拦不住（服务都在）。因此：**既然选择不设门禁，就必须把能力状态如实报出来**，否则未来版本上的静默失败将无人察觉。

这一条把 `CONTEXT.md` 里既有的「不可用能力必须给出明确原因」从**两分**扩展为**三分**：能力状态是**缺失**、**语义漂移**、**可用**；只报告"缺失"会让漂移长期不可见。

## Consequences

- 环境诊断必须对每项宿主能力给出**三态**报告（可用 / 语义漂移 / 未验证），而不是只报"服务在不在"。这是本决策成立的条件。
- 四处差异各自**双路径**：旧代走旧接口、新代走新接口，两条路径都必须被测试执行到。
- 由于只对新一代做真实宿主验证，**旧代路径靠假宿主夹具保护**——夹具须能模拟两代服务形状，而不是只表达"服务在不在"。
- 插件依赖的**宿主私有成员**（权限预设、工作区注册表的若干成员）必须补存在性守卫：它们今天能用，但没有任何契约保证。
- 去掉依赖上界后，**未来版本上的破坏性变更仍可能发生**。这是本决策明确接受的代价，其唯一护栏就是上面的显式报告——用户至少能看到"某项能力语义不符"，而不是面对一个安静失效的功能。

## Considered Options

- **按宿主版本号门禁**（设 `>=0.2.0 <0.3.0` 之类的区间）：简单可靠，但宿主不声明契约版本、可用性只能猜；且会挡住大量实际可用的组合。拒绝。
- **钉死精确版本**（只允许已验证的那一个版本）：最保守，也最不可用。拒绝。
- **推动宿主提供统一能力清单**（`host.capabilities`）：治本，但不由本插件决定，且当前诊断里也刻意不输出该汇总。不作为本决策前提。
- **保留依赖上界 `<0.3.0`**：能在包管理器层面挡住未验证版本，但与"不设版本门禁"自相矛盾——同一套哲学在包管理与运行期给出不同答案会让人困惑。拒绝。

## 与既有决策的关系

- 遵守 [0001](0001-mobile-git-scope.md) 的「能力缺失一律明确报错、不静默伪装成功」——本决策把它的适用范围从"缺失"扩展到"语义漂移"。
- **不改变** Git 能力接缝的 `contractVersion` 语义：那是提供者侧的声明式契约，与宿主侧的探测是两件事，不应混为一谈（`CONTEXT.md` 已把「兼容版本」与「宿主能力」分列两条，正是为避免这种混淆）。

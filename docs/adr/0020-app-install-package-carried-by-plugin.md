# 0020 App 安装包随插件分发：同包名的载体版本

状态：已接受。背景与验收见 GitLab `ahedu/dsh-mobile-remote#35`。

## 问题

App 与插件**强耦合**（只装一端没有意义，版本必须成对），但升级动作是分离的：插件在 profile 里升级，App 要另外找人要、找对版本、手动安装。三条实测事实让它变成真问题：

1. 手机端默认从 GitHub 取 APK，在本机环境下**不可用**（72MB 级资产 40 秒只取到 0.8MB；上游最新 Release 也没有清单资产）。
2. 宿主不一定持有与当前插件配对的 APK——更新目录默认未配置，需要人工放置。
3. 载体（APK）体积约 72MB，是插件包（3.6MB）的二十倍；把它塞进插件包会让每次插件升级都拖着 72MB，并污染插件的内容标识。

## 决策

**用同一个包名发布两个版本**：`X.Y.Z`（插件）与 `X.Y.Z-app`（App 载体版本）。主包以**精确**版本别名依赖载体：

- 载体内容 = APK + **完整 schema 1 发布清单** + 说明/许可；清单同时含两端身份，因此宿主在装完插件后**无需任何额外配置**就能得到配对信息。
- 载体使用独立 dist-tag（`app`），**绝不进入 `latest`**：否则 `npm i <包名>` 会把 72MB 的数据包当成插件装进 profile。
- 别名必须写精确版本：semver 上 `^X.Y.Z` 永远不会匹配 `X.Y.Z-app`（预发布），写范围等于永远拉不到。
- 载体只承担**数据角色**：不写 `os`/`cpu`/`libc`、包名与字段不含平台 token、不写 `bin`/`main`/`exports`、不写 `dsh.bundle`、无安装期执行钩子。原因很具体：pnpm 对 optional 依赖做平台匹配，且会从**包名**推断平台 token，被判定不匹配时**静默跳过**，而 DSH 的安装仍报成功。
- 运行时依赖闭包必须排除载体，但**不能**凭任意包自报标记豁免：只有「根包显式声明该依赖 + 真实包名/版本/数据角色标记/清单/APK 哈希全部校验通过」时才排除，且排除要贯穿建图、冻结复制、冻结后完整校验与恢复路径。否则每次自更新都会把 72MB 复制进产物目录和每个回滚快照。

## 为什么不是另外两种

| 方案 | 否决理由 |
|---|---|
| A：APK 直接放进插件包 | 单 tarball 约 75MB（发布请求体更大）；APK 进入内容标识范围会让「App 改一行」变成「插件内容标识变了」，与 ADR 0019 的判据冲突；**且仍需**激活、落位、寻址与鉴权逻辑，并不能省掉运行期工作。 |
| C：包外按需预取 | 需要新增宿主侧 APK 网络下载器、缓存回收、来源与重试管理；首次取件还依赖外网可达（而 GitHub 路径实测不可用）。 |
| D：同包名载体版本（本决策） | 复用既有包管理分发链，不需要新增取件代码；镜像按包名同步，国内可达性跟随用户已有的 registry 配置。代价是每次装/升级仍付约 72MB——这是「一次动作把两端一起升」的必然成本，不是实现瑕疵。 |

## 后果

**正向**
- 升级插件这一个动作就带入了配对 APK；配对由同一次发布决定，不靠人记。
- 国内镜像自动覆盖（发布走 npmjs、下载走镜像）；无需再找第三个镜像源。
- 宿主取件交给包管理器，运行期无需新增下载器。

**代价与风险**
- 每次安装/升级承担约 72MB 传输（含 CI 与多 profile 机器）。
- optional 依赖可能被静默跳过（平台字段、镜像滞后、`--omit=optional`）→ 必须由插件**自检**并给出三态诊断，不能假定「安装成功 = APK 到位」。
- 公共 registry 对该体积与形态**没有专项许可**：体积上限未公开、且「不得把公共 registry 当通用数据库」的政策条款存在被解释的空间。正式发布前需经一次有授权的真实发布验证；失败则回到方案选择。
- 测试通道不能复用正式版本号：插件没有构建号，测试包与正式包同号，因此**测试插件一律走 `file:` 目录依赖，不向任何 registry 发布**。

## 替代方案（未采纳）

- **另发一个独立包名**：用户视角仍是「装一个名字、多一次动作」，且要维护两条版本线的配对；收益不足以抵消。
- **把 APK 作为 Release 资产、宿主按清单地址下载**：被 ADR 0021 否决（宿主不自取）。

# 0019 两端版本偏斜：清单为权威、声明判能力、版本号只做提示

状态：已接受。背景与验收见 GitLab `ahedu/dsh-mobile-remote#32`。

手机 App 与桌面端插件分别发行，而**两条更新渠道的摩擦差一个数量级**：App 走 GitHub Releases 自助安装、并已具备应用内自更新（`feature/app-auto-update`）；插件要改 profile 依赖、`pnpm install`、再**重启宿主**。结果是偏斜会**单向恶化**——App 被持续拉新，插件停在旧版。

README「版本与兼容」早已给出政策：**任意组合可用、协议只加不删、禁止破坏性变更**。问题不在政策，而在**政策没有兑现机制**：现状只有三处靠 `not-found` 字符串判断「插件过旧」（`providers_screen.dart`、`settings_screen.dart`、`usage_screen.dart`），插件完全不读 App 版本，也没有任何测试强制新端点登记能力或文档。

本 ADR 记录三件事：**用什么判据、提示放哪端、谁来执行更新**。

## 三条判据各司其职

这是本决策的核心，也是与既有词汇最容易混淆的地方：

| 问题 | 判据 |
|---|---|
| 这个能力能不能用？ | **能力声明**（延续 ADR 0017 与 CONTEXT「时间线能力」） |
| 要不要下载新版本？ | **发布清单里的内容标识** |
| 要不要提示用户对齐？ | **版本号**（只决定提示文案） |

第二条是本次新增，理由是一个实测盲区：上游 `v3.2.0` 的插件与本仓库 develop 的插件**版本号都是 `3.2.0`，内容却不同**（develop 多出 `#19/#20/#21/#22` 等修复）。用版本号判「是否已最新」，这类差异永远不可见。清单里的 `sha256` 可直接取自 GitHub Release asset 自带的 `digest`，无需自建；另发布一个对 `lib/**` 规范化哈希的 `contentSha256`，使本地**可复算**而不依赖安装记录。

第三条不违反 CONTEXT 的「兼容版本」与「时间线能力」：那两条禁止的是**用组件版本推断能力可用性**；版本号在这里只决定提示文案。

## 发布清单是唯一权威，且源可配置

清单（schema 1）同时描述同一次发布的两端产物，与 App 侧既有的 `updateDir/manifest.json` **共用同一 schema**：App 从插件的 `updateDir` 取 APK，插件从发布者的清单取 tgz——一次设计、两处复用。

配置 `pluginUpdateManifest` 取 `"upstream" | "off" | <https URL>`，默认 `"upstream"`。这条解决一个真实冲突：**PR 必须指向上游，而维护者想握发布权**。硬编码任何一个都只能满足一半；可配置 + 默认上游同时满足两者，并让未来的 npm 源只是「另一个清单地址」。`"off"` 是必需品：自建/离线环境要能彻底关掉外发请求。

## 更新顺序：插件先行

README 保证「协议只加不删」，因此**新插件对旧 App 是安全的**（未知帧忽略、新字段忽略）；而**新 App 对旧插件不安全**（新端点在旧插件上不存在）。所以任何编排都必须**插件先更新、App 后跟随**——手机端从插件取 APK 正是这个顺序的自然结果。

## 提示放 PC 端优先，是为了解自举

已在用户机器上的旧 App 既没有对齐逻辑、也没有自动更新，所以「手机端提示」第一期覆盖不到它们。但插件升级后立即是新版，**且不需要 App 上报版本也能判**——「请求里没有 `x-mobile-app-version`」本身就是「这是旧 App」的信号。因此第一期把不一致提示放 PC 端优先，存量 App 第一次就能被覆盖；手机端提示作为第二期增强。

## 手机端可独立触发，不加 PC 二次确认

这是**产品取舍而非安全结论**：手机版的意义就是不依赖「人在这台电脑前」。若手机触发后仍需在电脑上敲命令，这个意义并未兑现。

代价必须一并接受：手机触发的路径**必须是端到端的**（下载 → 校验 → 原子替换 → `pnpm install` → 重启 → 回滚），且**无人值守**——所以失败回滚不是可选项。一期把端到端限制在**能可靠自重启的形态**（`dsh web` + systemd、前台 web）；其它形态明确降级为「降级指引」。`pnpm install` 会替换正在运行的插件目录，Linux 可用而 Windows 会失败，这也是 Desktop 留到二期的原因。

## Consequences

- **端到端与回滚是一个整体**：更新前对当前版本目录做快照，重启后插件启动自检（能否正常 bootstrap、版本是否符合），失败自动切回旧目录并再重启一次，**最多一次**——否则会出现重启风暴。
- **跨重启是正常环节，不是失败**：手机端必须持久化「更新进行中」的状态并在重连后接续，否则用户看到的是「连不上」，与真实的「正在升级」无法区分。
- **tgz 必须自包含**：`bundleDependencies: ["qrcode"]`，否则解包覆盖或离线安装会缺依赖。
- **能力登记需要强制机制**：三条判据里「能力声明」这一条现在只有 2 个特性被声明，其余靠 `not-found` 兜底；不补强制登记，判据分离会退化成口号。
- **提示不得阻断**：对齐提示只影响文案；能力缺失时仍按声明降级，不因「版本号相同」被判为可用。

## Considered Options

- **用契约版本号（`API_LEVEL`）做门禁**：直白，但要修订 CONTEXT「兼容版本」「时间线能力」，且把「能不能用」重新变成「版本够不够」——正是 ADR 0017 拒绝过的思路。只在提示层保留版本号。拒绝。
- **App 直连 GitHub Releases 取 APK**：现网就是这么做的，但 tgz 对手机无用，无法驱动「插件先行」的编排。清单统一后由两端各自取用。替换。
- **手机触发加一道 PC 二次确认**：更安全，但抵消手机版的核心价值。拒绝（代价用端到端 + 自动回滚对冲）。
- **插件热更新（不重启宿主）**：插件随宿主进程加载、路由随 fiber dispose 注销，没有热重载通道。拒绝。
- **更新源硬编码上游**：PR 可接受，但维护者失去发布权（上游最近 release 停在 `v3.2.0`，而 develop 已到 `3.2.0+44`）。拒绝。
- **更新源硬编码自建**：上游不会接受。拒绝。
- **vendored 覆盖（不解 pnpm）**：不依赖 pnpm、可离线，但会被下一次 `pnpm install` 静默回滚（`file:` 依赖是 directory 类型、无 integrity）。降为二期离线兜底。

## 与既有决策的关系

- **遵守并延伸** ADR 0017：能力判定继续走探测/声明；本次新增的「内容标识」只回答「要不要下载」，不回答「能不能用」。
- **不改变** README「版本与兼容」的政策（任意组合可用、只加不删、禁止破坏性变更）：本决策是给该政策补上兑现机制。
- **复用** App 侧既有的 `updateDir/manifest.json` 与 `/m/api/update/manifest`、`/m/api/update/apk`（`feature/app-auto-update`）：清单 schema 统一，两处共用。
- **领域词汇**：`CONTEXT.md` 在「两端版本与更新」小节新增「发布清单」「内容标识」「对齐提示」「插件自更新」「降级指引」「更新接续」六条。

## 1. 目标与边界

### 1.1 产品形态与判据

本项目由 DSH 插件和 Flutter/Android App 组成。插件提供移动端接口，App 提供手机交互。

本设计中的“成对”指**同一份发布清单绑定两个确定的产物**，不是“只有相同版本才能使用”的能力门禁。继续遵守 [领域词汇](<../../CONTEXT.md#L297-L323>) 与 [ADR 0019](<../../docs/adr/0019-version-skew-between-app-and-plugin.md>)：

- 能力能否使用，看能力声明；要不要下载，看内容标识；要不要提示对齐，看版本号。
- App 的 `sha256` 确认 APK 身份；插件的 `contentSha256` 确认正在运行的代码是否为配对目标。二者缺一不可。
- 日常使用不因版本不同被一刀切拒绝；但自动更新编排必须先确认目标插件健康，再安装同一发布快照中的 App。

### 1.2 用户目标

1. 正式安装或升级插件时，由包管理器把配对 APK 一并带到宿主，不再要求用户另外寻找 APK。
2. 插件实际生效后，手机从宿主可达地址下载 APK，不依赖手机下载 GitHub 大文件。
3. 全新手机可扫描电脑连接页上的二维码，**匿名下载 APK**；移动控制接口仍须鉴权。
4. 下载、校验、重启、回滚、断线重连均有明确结果和恢复出口，不把“插件已装好”误报为“两端更新完成”。

“一次动作”是分发目标，不是静默安装承诺：宿主仍可能要求重启使插件生效；Android 仍需授权安装来源和确认系统安装器。插件管理器报告包安装完成，不等于新插件已经激活或 APK 已可服务。

### 1.3 开发测试与正式发布

| 场景 | 规则 |
|---|---|
| 开发测试（App） | 使用 `X.Y.Z+N`，只走本地／私有测试通道；不向 npm 公共仓库发布这些测试构建 |
| 开发测试（插件） | 插件版本号没有 `+N`，与正式版同号；**测试插件一律用 `file:` 目录依赖，不向任何 registry（含私有）发布**，避免与正式 `X.Y.Z` 撞号 |
| 正式发布 | 对外版本、正式包版本和发布名使用 `X.Y.Z`；插件 npm 版本为 `X.Y.Z`，载体为 `X.Y.Z-app` |
| Android 内部身份 | 正式 APK 仍保留真实、递增的 `versionCode`；机器清单中的 `app.version` 保留 `X.Y.Z+N`，用于现有更新判定，不把构建号从校验中抹掉 |
| npm 不可变性 | 同一包名的 `X.Y.Z` 和 `X.Y.Z-app` 均只能对应一份已发布内容；修订正式产物必须申请新的正式版本，不能覆盖重发 |

正式版的对外命名不改变 Android 的防降级约束。开发 APK 若已占用更高构建号，后续正式 APK 的内部构建号也必须更高。保留“同语义版本不同内容”的内容标识检测能力，不等于允许覆盖 npm 版本。

## 2. 事实、历史测量与本次缺口

### 2.1 现有代码可确认的事实

下表的“现有”不代表本方案已打通；代码位置见第 9 节。

| 编号 | 事实 | 设计含义 |
|---|---|---|
| C1 | Android 当前采用系统安装器；更新前有大小、哈希及签名预检，系统阻止更低 `versionCode` 的安装 | 不自动降级 App，正式发布也不能省掉内部构建号 |
| C2 | App 按候选中的绝对地址直接下载 APK，不解 npm tarball | npm 是宿主分发通道，不是手机下载通道 |
| C3 | 内容标识实现覆盖根包元数据与代码目录，排除依赖目录 | 根目录或其他代码目录之外的 APK 不会天然进入插件内容标识；修改主包中的载体依赖声明仍会改变该标识 |
| C4 | 当前更新目录默认未配置；本地主机源读取目录内已有清单，不会自动生成或同步清单 | 载体仅带 APK 不够，必须定义清单到达、默认目录和激活规则 |
| C5 | 外部发布源的快照保留外部下载地址，现有客户端投影仅处理回环主机源；App 默认源为 GitHub | 本地落位不自动把手机切换到宿主下载，必须修改来源接线 |
| C6 | 当前 APK／插件下载路由每次重读当前清单；固定快照只固定元数据，没有固定可取字节 | 必须增加不可变产物寻址，并为接续保留旧目标 |
| C7 | LAN 桥重写 Host 为宿主回环地址，而地址投影读取 Host | 存在给手机返回 `127.0.0.1` 的路径，不能宣称现有投影无需修改 |
| C8 | 现有移动接口认证接受访问口令请求头或 Cookie；未配置口令时会关闭认证 | 首装浏览器不能直接复用 App 的请求头；本次明确收紧无口令行为，而不是沿用此默认姿态 |
| C9 | 冻结运行依赖会遍历普通及 optional 依赖，且冻结后再次验证完整闭包 | 载体排除要贯穿建图、复制、验证、复用与恢复，不只是少复制一个目录 |
| C10 | 监督器当前主要按正在运行的插件内容标识确认健康；App 另有插件优先门禁和持久接续记录 | 插件健康、APK 就绪和 App 安装确认是三个不同结果；现有接续仍需补失败恢复出口 |

### 2.2 原调研记录：不能直接外推为保证

以下保留为 2026-10-19 初稿的环境记录，本轮未重新访问 registry、运行中宿主或真机复测：

- APK 约 70.4–71.9MB；**载体 tarball 实测 35.9MB**（75,434,367B APK → 35,885,383B，gzip 压缩 2.1×），插件 tgz 约 3.6MB。首次冷安装预算约 **40MB**（**不是**此前估算的 75.5MB）；实际流量受压缩、包缓存及内容复用影响，不是每次必付的定值。
- 曾观察到 npm 在架 113.5MB tarball、社区约 229.9MB 请求被拒，以及 CLI 的内存／请求体限制。这些记录**不能证明 npm 的公开保证上限，也不能称为当前最大包**。
- npm 发布请求把 tarball 以 base64 放进 JSON，体积约增加三分之一。**P0 实测**：35.9MB 载体的发布请求体约 **47.85MB**（本地 Verdaccio 测得），远低于 100MB 级门槛，Cloudflare 免费版 100MB 的限制因此不构成阻塞；公共 npm 真实接收仍需授权后验证。
- Codex 同包名平台变体及别名依赖是技术先例；原调研看到的大型 vendor／可执行文件体积，不等于 npm tarball 的压缩体积或本 APK 已获接收。
- 当时 DSH 枚举主要依据 Loader 与 profile 的直接依赖，不把传递载体列为插件；optional 跳过不会阻止管理器报成功。此行为必须作为兼容夹具保护，不能外推所有未来宿主版本。
- pnpm 11.22.0 的 optional 依赖可因平台／解析问题被跳过；包名推断平台 token 是载体命名约束的来源。
- semver 不会让 `^3.2.1` 接受 `3.2.1-app`，因此主包仍固定精确载体版本，载体绝不进入 `latest`。
- 当时两开发线的更新机制文件相同、入口代码差异较大；运行内容与 develop 一致。这是当时快照，不代替实施前重新核验基线与运行身份。
- 当时本机 GitHub 大资产下载很慢，而 registry 响应较快；**元数据请求时延不等于 72MB tarball 的吞吐测试**。上游当时的最新 Release 没有清单资产，也不是永久事实。

### 2.3 本轮必须修正的缺口

本次不仅增加 npm 载体，还必须补齐：配对清单随包到达、当前发布与待更新目标分离、固定快照定位、可信地址投影、匿名 APK 与控制鉴权分流、多写者所有权、保留与回滚，以及 App 接续失败出口。不能再标注“运行时代码无”“App 零改”或“更新事务机制完全不动”。此外还需明确无口令安装的迁移路径：口令从何而来、用户如何得知需要重扫一次。

### 2.4 P0 可行性实测（2026-10-20，隔离环境）

三条结论全部成立，且纠正了初稿的两个估算：

| 结论 | 实测 |
|---|---|
| A 真实包管理器能取得载体 | registry / tgz / `file:` 三种形态下，精确别名均被 pnpm 11.22.0 真实安装到 `node_modules/<别名>/`（真实 name/version 正确、APK sha256 与仓库一致）；**自更新把 profile 依赖从 registry 改成 `file:<产物目录>` 后 `pnpm install` 也正确换装新配对载体** |
| B 载体打包与分发成立 | 真实 APK 75,434,367B → 载体 tarball **35,885,383B**（`npm pack` 3.1s）；本地 Verdaccio 发布成功；默认 `max_body_size=10mb` 触发 E413，实测需 ≥**50mb**（发布请求体约 47.85MB） |
| C 版本约束成立 | `^X.Y.Z` 不匹配 `X.Y.Z-app`；载体只进 `app` tag；**别名若写范围（`^3.2.0`）会把主插件错误装进别名目录**——精确别名是硬要求，已有反例 |

必须写进实现的三个实测失败模式：
1. **optional 载体缺失时 pnpm 静默跳过**（rc=0、无警告）→ 运行时诊断必须自建，不能依赖包管理器提示。
2. **pnpm 11 忽略 `package.json` 的 `pnpm.overrides`**（须写在 `pnpm-workspace.yaml`）→ 影响测试通道的本地绑定写法。
3. **hoisted + 本地载体目录 override 落盘异常**（别名错放主包）；本地载体 **tgz** override 或 isolated + 目录 override 才正常 → 测试通道实现按此选择。

仍未关闭：**公共 npm 的真实大包接收与镜像延迟**需授权后验证；若失败则必须阻止 D 进入正式发布。

## 3. 方案选择及修正后的比较

| 方案 | 做法 | 主要代价 | 内容标识与运行期责任 | 本次结论 |
|---|---|---|---|---|
| A 单 tarball | 插件包直接携带 APK | 单包约 75.5MB，发布请求更大 | APK 可放在哈希范围之外；仍需激活、落位、寻址及鉴权逻辑，不能以“必然污染哈希”淘汰 | 本轮不采用，但保留为真实备选 |
| C 包外预取 | 插件安装／激活后自动从外部源取 APK | 增加下载、重试、来源及缓存管理 | 完全可以保持用户一次动作；代价是运行期网络路径，而非必然多一次人工操作 | 本轮不采用 |
| D 同名版本变体 | 同包名发布插件及 APK 载体，以精确别名依赖相连 | 包管理器承担大文件传输；optional 可能缺失 | 仍需载体发现、清单验证、托管发布、固定寻址和诊断 | **保留；以 P0 验证为前置条件** |

保留 D 的依据是利用既有包管理分发链，避免新增宿主 APK 网络下载器；不是“D 没有运行期复杂度”。若关键安装或发布验证失败，停止进入正式发布，回到方案选择，不在事务结束后偷偷补装依赖。

npm 技术先例不等于平台政策认可。[npm 条款](https://docs.npmjs.com/policies/open-source-terms/)保留内容处置权；[版本发布规则](https://docs.npmjs.com/cli/commands/npm-publish/)禁止复用已发布版本。本方案不声称已取得 npm 对 APK 载体的专项许可。

## 5. 工程契约（本次拟实现）

### 5.1 产物与随包清单

每次正式发布形成三组产物：

| 产物 | 内容与约束 |
|---|---|
| 主插件 `@marktrue/dsh-mobile-remote@X.Y.Z` | 精确声明 `"@marktrue/dsh-mobile-remote-app": "npm:@marktrue/dsh-mobile-remote@X.Y.Z-app"`；载体不进 bundled 依赖；代码哈希按现有算法生成 |
| 同名载体 `@marktrue/dsh-mobile-remote@X.Y.Z-app` | 包含 APK、**完整 schema 1 发布清单**及说明／许可证；`dsh.appCarrier: true`；不承担运行入口和插件 bundle 角色；实测 tarball 约 35.9MB（APK 75.4MB，gzip 2.1×） |
| Release 三资产 | 同一份清单、同一 APK、**同一已打好的主插件 tgz**；文件名、大小与哈希逐字节一致 |

载体文件列表示例：

```json
{
  "name": "@marktrue/dsh-mobile-remote",
  "version": "X.Y.Z-app",
  "files": ["DSH-Remote-vX.Y.Z.apk", "manifest.json", "README.md", "LICENSE"],
  "dsh": { "appCarrier": true }
}
```

清单同时包含完整 `app` 与 `plugin` 段，以及现有顶层兼容镜像；`app.version` 使用真实 `X.Y.Z+N`。插件段必须有版本、文件、大小、tgz 哈希、内容标识，并有可明确解析的下载定位。嵌入载体后不再依赖“相对 latest 清单地址猜测 tgz URL”：必须提供版本固定的绝对定位，或由已校验的本地主机产物提供固定定位。

载体不必再塞一份插件 tgz。没有本地 tgz 时，不得虚构一个可服务的主机插件下载地址；恢复快照仍独立自包含。哈希提供内容一致性，不代表发布者身份认证；信任仍来自受信任安装渠道、配置的清单来源和 Android 签名策略，不导入任意客户端提供的包路径或下载地址。

### 5.2 构建与发布：先打插件包，后发布载体

1. 在实际发布的干净 HEAD 上固定主包元数据、载体依赖和版本；完成 APK 构建，确认应用身份、真实构建号及签名。
2. **先打好主插件 tgz**，计算它的字节哈希和解包后可复算的内容标识。
3. 由该 tgz 与 APK 生成完整配对清单，再把 APK 和清单打入载体。这避免“插件包内部清单包含自身 tgz 哈希”的循环依赖。
4. 校验两个包、APK、清单及构建证据一致。不得在此后修改主包或重新 pack 出另一份 tgz。
5. 经正式发布授权后，先发布载体到 `app` tag，核验实际 registry 中的版本、tarball 与声明支持的镜像可取得性，再发布**步骤 2 的同一 tgz**到主插件渠道。
6. 发布同一套 Release 三资产，核验公开可取的字节，不只看发布命令退出码。跨 npm／Release 不具备原子事务，必须记录部分成功；重试复用已成功的同一内容，不覆盖已有版本。

发布窗口内主插件尚不可解析（`pnpm add` 得到 404）属**预期 fail-closed**，须记录在发布记录与运维预案里，不当作缺陷。测试插件不发任何 registry（见 1.3），P0 的 `file:` 布局验证即覆盖测试链路。

测试产物只在隔离 profile／本地或私有源验证。P0 必须证明测试主包能精确绑定本地测试载体，不会误用 registry 中同语义版本的正式载体；本地安装布局亦按内容区分，不覆盖生产缓存。具体 pnpm 本地 override／目录依赖写法由验证结果固定，不能把尚未验证的命令写成可用方案。

fork 与上游若代码不同，就不能用同一个 npm 包名和版本发布两份内容。移植、集成后必须按**实际要运行的 HEAD**重新形成并验收相应配对产物；不得把功能分支清单直接用于内容不同的 develop。正式版本分配仍需授权，本稿不批准 bump 或改写历史。

### 5.3 清单角色：当前发布、更新目标、固定快照

三者均引用发布清单，但职责不同：

- **当前发布**：配对插件的内容标识等于当前服务实例实际加载的内容，并已满足健康确认；用于当前首装入口。来源为已验证载体或先前保存的配对清单，不取决于远端 latest。
- **更新目标**：用户选中、由宿主受信来源解析的一次发布，可早于实际安装进入候选状态；它不能把当前首装入口提前指向尚未生效的插件配对 APK。
- **固定快照**：一次更新受理后冻结的两端产物身份；后续换源或发布新版都不替换其目标。

**当前发布的判定（可执行定义）**：当前发布是**唯一**满足「清单 `plugin.contentSha256` 等于本实例实际运行内容标识」且健康结果已确认的记录；人工区与托管区等多个来源命中同一身份时去重为一条；无命中时当前入口**不可用**，绝不退而取 latest。

鉴权 bootstrap／主机清单应独立提供 `currentRelease`（完整快照、`releaseId`、宿主固定 APK 定位）、`currentReleaseHealth`（确认／等待／失败、实际运行内容标识、服务实例身份及关联事务代际），与 `updateTarget`、外部检查状态及 `transaction.release` 分开；旧字段只作兼容，不用一个 latest 字段兼任三者。人工区作为主机更新源时仍可预置尚未安装的完整目标，不得被当前发布遮蔽；发现候选不以 APK 已落位为前提，其就绪状态单独报告。本机清单路由读取已验证的本地发布记录，不递归请求配置中的同一路由；外部发现的结果作为独立候选记录接入。

无接续记录且只需安装当前配对 App 时，新 App 直接消费上述本地快照和健康结果启动 App-only 更新，不查 GitHub，不因独立的 disabled／unavailable 状态一概拒绝。用户选择新插件目标时才进入该目标的两端编排；已有 journal 时始终核对原 `releaseId`，不能换成 current／latest。接入通过新增能力声明与可选字段完成，旧宿主没有相应能力时保留明确的兼容／迁移提示，不按版本猜能力。

主机增加不依赖外部地址的 `releaseId`，用于存储和传输定位：对版本化、规范序列化的两段产物身份字段求哈希，字段包括两端版本、文件名、大小、字节哈希及插件内容标识；不包括请求方 URL、备注和临时地址。它不取代既有内容标识，也不作为能力门禁。精确序列化和测试向量属于 P0 契约：前缀固定 `releaseId/v1`，P0 落 2–3 组固定测试向量，并规定**只增字段、不改既有字段的序列化顺序与归一化规则**；改变序列化必须提升版本前缀。同一身份经不同来源到达时，不覆盖不可变身份记录；源地址与信任上下文按 profile／受理事务保存，不能因共享缓存改写另一 profile 的下载定位。

插件安装后不用手工配置清单即可验证当前配对：载体清单中的插件内容标识必须等于本实例运行内容，APK 的大小、哈希和预期包身份也必须通过检查。旧目录中的 A 清单即使完整，也不能让新插件 B 错把 A 认成自己的配对。

健康结果不是文件指针或哈希相同的别名：自更新要求目标事务健康确认并 settled；初次／手工预装允许以本实例实际激活、配对内容核验通过且无矛盾在飞事务为依据，不强求不存在的旧操作；回滚则要求监督器明确确认旧内容已恢复且实际运行匹配。正在安装、等待重启、回滚中或恢复未确认时不报告 confirmed，历史失败标志也不能永久否定后来独立确认健康的当前发布。

`pluginUpdateManifest` 继续决定外部更新发现来源；关闭或暂时无法检查远端，不应否定**已经本地完整验证且健康的当前配对**。这只允许继续本地 App 安装；`off` 下不新建插件自更新事务，也不以隐式换源或本机清单自环规避关闭设置。

手机触发插件更新时提交操作身份及所选 `releaseId`。宿主只能从自己已经验证、可解析的发布记录中受理该目标；不相信客户端自报的 URL、哈希或路径。目标变了就明确拒绝／要求重查，不允许手机选 B 而宿主悄悄重新检查并执行 A。固定快照和引用保留必须在返回受理结果前持久化成功。

### 5.4 默认目录、所有权与发布协议

配置的 `updateDir` 非空时使用该目录；未配置时，自动载体分发使用 `~/.dsh/mobile-remote/update`。这是本次新增默认行为，不再依赖用户手工开启主机更新目录。文件系统不可写则给出降级诊断，不能伪装已就绪。

目录布局示意（字段与文件名是拟实现契约）：

```text
<effectiveUpdateDir>/
  manifest.json / APK / tgz           # 既有人工区；插件不自动改写或清理
  .app-carrier/                      # 自动托管区，带所有权与布局版本标记
    objects/apk/<appSha256>/app.apk   # 只读 APK 对象
    objects/plugin/<tgzSha256>/plugin.tgz  # 仅在实际导入本地 tgz 时存在
    releases/<releaseId>/manifest.json
    profiles/<profileKey>/current.json
    leases/                          # 与既有事务代际绑定的持久引用
    staging/                         # 未提交产物，不参与服务
```

- `profileKey` 来自验证后的当前 profile 身份；不同 profile 的当前指针不得共用。不能从 web／desktop／cli 中“找到第一个就用”。无法确定本 profile 时明确不可用，不猜其他 profile。
- 所有自动写者、恢复选择和 GC 通过同一个托管 module 与锁／提交协议访问托管区。已有目录若无合法所有权标记或布局版本未知，不接管、不递归清理，给出诊断。
- 在暂存区先完成清单、APK 身份和完整性检查，再发布不可变对象及发布记录，最后原子更新本 profile 指针；对象验证失败或进程中断不能留下可服务的半成品。
- 对象提交禁止原地覆盖已发布 inode：先建立暂存目录项，再以同文件系统原子 rename 发布；载体硬链接可共享同一只读 inode，复制及人工导入必须使用独立新 inode。需要保证崩溃恢复的提交按平台能力同步落盘。所有者权限不允许时不以不安全覆盖兜底。
- 硬链接仅从已核验且按约定只读的载体文件建立；两端都不能原地写。链接不支持、跨文件系统或权限受限时复制到暂存新文件；**绝不移动载体原件**。
- 手工区导入一律校验并复制为独立托管对象，不与后续可能被人工覆盖的文件共享 inode。手工文件发生变化时，旧快照仍服务已导入的旧对象。
- 发布脚本的托管模式调用相同提交协议；原有人工导出模式只写人工区，改为先暂存后提交且清单最后发布。插件只在完整校验通过后导入，因此不把三件套普通 `cp` 视为原子发布。
- 更新事务需要的锁顺序固定为“既有更新租约 → 托管区提交锁”；GC 只取托管区锁。持有目录锁时不等待网络、pnpm、宿主重启或另一把更新锁；丢失事务代际的写者不能提交指针、引用或清理。

缓存中的 `current.json` 是选择结果，不是运行健康证明。每个 HTTP 实例仍依据自身实际加载内容和事务状态判断；过期激活实例不得覆盖新代当前指针，正式回滚可在新代重新选择旧发布。

### 5.5 载体发现与运行依赖排除

从本插件自身的解析作用域定位载体别名下的包元数据，不解析无入口载体的裸包入口，也不照搬扫描其他 profile 的查找方式。必须核对：声明的精确 npm 别名、真实包名／版本、`appCarrier` 标记、完整清单、允许的文件路径及 APK 哈希。

排除只适用于根包明确声明且身份验证通过的载体数据依赖；任意普通依赖自报 `dsh.appCarrier` 不能绕过验证。建图阶段在要求可执行入口前识别载体；冻结、隔离验证、快照复用与监督器恢复采用一致规则。保留根包元数据原样，不通过删除依赖声明改变内容标识；qrcode 等真正运行依赖仍须完整验证。

载体不进入 profile 的直接依赖或宿主 bundle 列表。若真实 `file:` 自更新布局不能安装所需载体，P0 阻止 D 进入正式发布；不得在已 `settled` 后执行 `pnpm add` 写 profile 或绕过既有租约／快照。

建议把发现、校验、落位、选择、打开对象和引用回收放在一个深 module 后面；入口只保留小 interface 的接线。该 interface 是测试面，不把并发顺序和目录知识散落到 HTTP callers。拟新增文件名由实施时确定，本稿不要求先拆出一批浅转发 module。

### 5.6 下载接口与地址投影

保留现有 APK 路径，并扩展以下语义；以下路径均相对实际插件挂载路径，非硬编码 `/m`：

| 请求 | 契约 |
|---|---|
| `GET /api/update/apk` | 当前配对 APK 的匿名首装入口；按实际运行内容选择并一次性打开确定文件，不先发布未确认目标 |
| `GET /api/update/apk?release=<releaseId>&sha256=<appSha256>` | 固定目标匿名下载；两个标识都须合法且与记录一致，绝不替换为 current 或 latest；HEAD 若支持，采用相同权限与身份规则 |
| `GET /api/update/manifest`、bootstrap 与更新受理响应 | 仍鉴权；明确区分候选和当前配对。无固定参数的主机清单提供该主机源中已验证的更新候选，无候选时可返回当前配对但必须标明角色；加 `release=<releaseId>` 只返回指定记录。新流程的 `app.url` 均为手机可达的宿主固定目标地址，不因原始来源是 HTTPS／GitHub 而例外 |
| `GET /api/update/plugin?release=<releaseId>&sha256=<tgzSha256>` | 仍鉴权；只服务实际导入的不可变 tgz，同样受固定身份、引用与保留规则保护；缺本地对象时不提供该地址，而保留可信的版本固定源定位。旧无参数路径只作兼容入口，不能写入新固定快照 |

机器快照保留固定产物身份，客户端投影只改定位，不改哈希、版本或清单身份；内部 worker 继续使用其受信源／回环定位，不能把手机 LAN 地址写回内部事务。

地址投影不能继续直接照抄桥后的 Host。web 直连及 LAN 桥均须按实际本机网卡／监听端口，或显式配置的对外 authority 白名单校验地址；协议取真实 TLS／监听配置，不由客户端转发头决定。反向代理场景只采信显式受信的代理来源和配置的对外基址，不能把任意传入 Host／端口盖上内部 nonce 后就当作可信。桥去掉客户端伪造的同名转发信息，再以仅内部可验证的来源元数据传给上游；上游仅在回环来源及内部凭据均匹配时采信。保留自定义挂载路径与合法代理部署，不接受任意 `X-Forwarded-*` 构造下载地址。

固定目标响应支持 `Range` 与 `If-None-Match`／`ETag`（ETag 由 `releaseId` 与对象哈希派生），断线可续传；不支持时至少保证同一地址始终返回同一字节序列。读取同一个已打开文件句柄完成必要的完整性复核和响应；流开始后发布、重命名或 GC 不得把内容切成另一份文件。不在宿主事件循环里为每个匿名请求同步读入并哈希整个 72MB 文件；采用导入校验、受控复核和流式读取，文件变化必须被检测或按不可变对象契约拒绝服务。

### 5.7 匿名 APK 与控制鉴权

- 匿名例外只匹配明确的 APK 下载路由、允许的方法及受校验的产物标识；不能因 URL 含有 `update` 就豁免整个前缀。
- 会话、消息、审批、文件、bootstrap、清单、诊断、插件 tgz 和更新写接口均继续鉴权。口令未配置时返回明确的“认证未配置”错误并拒绝访问，不再把它解释为关闭认证。
- **口令为空时由宿主自动生成**：`crypto.randomBytes(32)` 的 base64url 值，存插件状态目录（**不写入用户 profile 配置**）；`GET /api/qr-config` 返回该值，连接二维码因此仍“扫码即带口令”。自动生成值与用户显式配置的口令行为等价，配置非空时以配置为准；迁移期 App 需重扫一次，连接页与诊断须明确提示，不得让用户误以为服务故障。
- 唯一无需移动口令的本机配置特权入口为 `GET <basePath>/api/qr-config`，只读返回本机连接信息（可能含口令），不是远程移动控制豁免。它必须来自受信本机上下文，并通过实际连接来源与 Host 围栏校验；LAN 桥和任何远程反向代理均不得透传，不能只凭被代理后的回环 socket 判定“本机”。代理部署须在转发面显式排除此路径，宿主亦须拒绝能识别出的代理来源；无法建立可靠本机来源隔离时不开放此特权响应。匿名 APK 路由不能绕到它或其他文件。
- 现有本机二维码图片编码只处理调用方给出的文本，不额外读取口令配置；它同样不得经远程代理或 LAN 桥暴露，不能借图片编码另开配置数据出口。
- 不把长期口令放进下载二维码、URL 或 Referer；“已安装 App”的现有连接码仍可按既有本机展示规则携带口令，两种二维码不可混用。
- 匿名下载只服务指定 APK，保留 Host／来源围栏与路径约束；有独立、有限的并发、速率和连接资源保护，不让匿名请求消耗、重置或绕过控制登录的失败限流桶。
- 匿名下载不是“仅局域网”保证；若对应端口对公网可达，APK 也公开可取。它不授予控制权限，不随包携带口令、个人配置或宿主路径信息。
- APK 匿名例外不取消 LAN 桥启动时既有的口令要求。尚未建立手机可达监听时，页面必须说明配置问题，不生成指向死端口的首装二维码。

这是对现有“未配置口令即关闭认证”的明确策略变更，须写入迁移说明和验收；不得借此修改整个 DSH 或其他插件的鉴权模型。

### 5.8 保留、事务引用与回收

1. 当前发布的 APK 不因时间到期被删除。按 **profile 与真实选用周期**记录旧发布／目标被替代的时间，默认再保留 **24 小时**；重启或重复请求不能重置此时钟。从未成为当前发布的已导入失败目标，在对应事务终态或该候选真正撤回／被替代时起算；仅未提交的暂存文件不算可接续目标，可在确认无有效写者后回收。
2. 已受理更新事务在返回受理结果前，持久引用目标及可用的回滚前发布；保留信息与原事务身份／代际绑定，宿主重启后继续有效。提交引用失败则不受理破坏性更新。
3. 有效非终态事务引用，以及已打开响应句柄保护的对象，不在使用途中删除。终态释放事务引用，但不能因此缩短已经承诺的 24 小时保留窗口。
4. 不是“只要磁盘上有旧事务 JSON 就永久保留”：死持有者、超时及遗留中间态必须依既有租约／恢复规则收敛；先确认不再是有效引用，再回收。匿名 GET 不续租；响应连接也有有界资源及超时约束，不能用慢连接无限保活。
5. GC 汇总所有 profile 的当前引用、保留截止时间和有效事务引用，取其保护并集；例如两个 profile 先后在 0 小时与 23 小时弃用 A，后者仍须获得自己的完整 24 小时窗口。同一 APK 哈希仍被任何当前发布使用时不能删除。真实重新激活后再次被替代是新选用周期，但不是重启或请求刷新计时。
6. GC 在同一锁内复核标记、身份与引用，只删除托管区中属于本 module 的对象；保留足以识别已过期目标的元数据。未知文件、人工区、载体原件及 pnpm store 不属于 GC 权限。
7. 目标已过保留窗口、没有有效引用且不再可服务时，固定地址返回 `410 app-artifact-expired`，手机退出旧候选并提示重新检查；**不把旧 URL 重定向到新版**。APK 缺失但尚未就绪用 503 区分，不能把所有失败混成 404。
8. 过期是缓存可用性状态，不是永久撤销内容身份。相同发布经受信重新导入、或在健康确认的重新激活／回滚中恢复了原字节后，可将同一 `releaseId` 恢复就绪并更新墓碑；原 URL 仍只能取得原字节。匿名 GET 本身不触发复活或续期；已结束的手机旧流程仍须显式重查，不自动重启。

9. GC 前先核对 profile 存活性（profile 目录与 `package.json` 仍存在）；不存在的 profile 指针先写墓碑再释放引用，避免遗弃 profile 永久占用 APK。

对象状态机（实现与测试对齐用）：

```text
staging（不可服务） → published（可寻址） → current / target（被选择）
                                          → superseded（24 小时保留窗口） → expired（墓碑，410）
```

本规则限制的是托管 APK 的保留，不承诺整机只有一份 APK；包管理器自己的缓存和跨文件系统复制可能额外占用空间。空间不足时明确降级，不能擅自删除有效事务目标或手工文件。

### 5.9 回滚与 App 最小修改

- 升级开始时保留旧配对元数据和可用 APK；不把它们塞进执行代码快照。代码恢复后，按**已恢复实例的内容标识及健康结果**重新选旧发布，切回当前首装／下载入口；不靠版本字符串猜配对。
- 无法取得旧配对清单或 APK 时，当前入口显示不可用，不让新发布冒充旧发布，也不从外网自动补取 APK。新版对象可继续留在保留窗口内，不等于仍被宣传为当前发布。
- 固定目标地址仍只代表原字节；它不会随当前入口切换而变更。缓存保留与当前发布选择是两个独立动作。
- App 的插件优先门禁同时检查固定快照、正在运行的内容标识、健康结果及在飞／回滚矛盾；有效本地证明可支持远端检查关闭或失败时的本地 App 安装，不放宽目标不一致的情形。下载前及拉起安装器前重新鉴权读取当前状态，核对服务实例与事务代际；无法复核时不靠旧缓存证明启动安装。
- `appPending`／`pluginConfirmed` 也必须处理目标改变、过期、失败和另一事务回滚，提供明确取消旧目标／重查出口，不能永久显示“更新进行中”又拒绝重试。若回滚正好恢复了原候选配对内容，只能依据已确认的恢复结果重新建立证明，不能仅凭哈希相同绕过在飞状态。
- 拉起安装器不算完成；App 重启后核对真实安装版本／构建号，再确认 App 半程。若本机 App 已更高，不尝试降级，提示重新对齐。装完首次启动还须复核配对：若插件已回滚或运行内容标识与快照不符，明确提示“两端不匹配，请重新检查”，不自动降级、不静默继续。
- 仅修更新源接线、快照消费、门禁与接续。不扩展聊天、模型或其他日常功能。

当前首装入口只推荐与健康插件配对的 APK；**匿名下载不等于能控制浏览器何时安装**。下载后宿主可能回滚，用户也可手工保存安装包，不能把 App 内门禁宣称为所有侧载行为的绝对保证。已有高版本 App 与回滚插件按能力声明降级，不自动卸载或降级 App。

### 5.10 就绪、降级及错误语义

插件健康、APK 就绪、两端完成分开报告。保留 `appArtifact` 的 `ok / missing / mismatch` 分类，并给出稳定 `reason`、发布身份及可用的修复指引；不要返回凭据或本机绝对路径。

| 情形 | 对外结果与恢复 |
|---|---|
| 安装完成但插件未激活／健康未确认 | 当前下载入口不切到目标，显示等待激活／重启；不能宣称两端完成 |
| 插件健康但载体省略、镜像滞后或不可读 | 插件可正常工作，APK 分发降级；`503 app-artifact-not-ready`；手机保留可重试的固定目标，不仅因缺 APK 就回滚健康代码 |
| 载体／清单／APK 身份不符 | `mismatch`，不服务错误字节；按原因提示检查来源或手工放置 |
| 当前运行内容没有可信配对清单 | 入口不可用，不能退而取远端 latest；提示补齐同次发布的完整描述 |
| 托管区只读、磁盘满或所有权异常 | 明确配置／空间诊断，不落半成品、不清人工区；给出更换目录或手工恢复说明 |
| 固定目标过期 | `410 app-artifact-expired`；明确结束旧目标、重查，不静默换包 |
| 固定标识非法／未知 | 400／404 稳定错误；不把请求参数当任意文件路径 |
| 未配置口令／凭据错误 | 除精确的匿名 APK 路由及 5.7 所限定的受信本机配置入口外，受保护移动接口分别报认证未配置／401；不执行控制副作用 |
| 插件回滚 | 恢复旧配对当前入口；手机不先装失败目标，不尝试降级已装 App |

“重装插件”只用于依赖确实未完整安装等可修复原因；若平台策略、持续省略 optional 或镜像仍缺失，重装同样会失败，应先解决原因。手工兜底需提供 APK 和与当前／指定发布一致的完整清单，经同一导入校验后服务。

## 6. 实施阶段、门禁与验收

### 6.1 阶段顺序

| 阶段 | 工作与退出条件 |
|---|---|
| P0 可行性 | 隔离验证载体打包、精确别名、真实 pnpm registry／tgz／`file:` 安装、测试载体绑定、闭包排除及清单无循环；先不发真包。大包 registry 接收另需发布授权和真实证据，dry-run 不能代替 |
| P1 托管 module | 清单与身份验证、默认目录、profile 隔离、暂存／原子提交、固定对象打开、引用及 24 小时 GC；接口级隔离测试通过 |
| P2 插件接线 | 激活与就绪诊断、当前／目标分离、受理固定身份、LAN 可信投影、匿名 APK 窄例外及无口令拒绝；新旧鉴权边界测试通过 |
| P3 App 与连接页 | 最小来源／门禁／接续修复；双选项卡首装 URL；处理过期、回滚及重查，不永久等待 |
| P4 集成验证 | 按授权集成到 develop，再从实际集成 HEAD 形成配对测试产物，完成回归和真机验收；不得先正式发布分支产物再用不同内容做验收 |
| P5 正式交付 | 获版本／发布授权后，按 5.2 发布不可变正式两包及 Release 三资产；核对公开字节与运行内容；领域与 ADR 记录在 develop 落地 |

开发测试 `+N` 不发布公共 npm，不改运行 profile，不接管其他写入者。真实服务测试、安装、发布及重启仍遵循仓库现有授权流程，本稿不自动授权这些动作。

### 6.2 必须覆盖的验证矩阵

| 编号 | 场景 | 必须满足 |
|---|---|---|
| F01 | 干净 profile 安装主包与载体，未手工填更新目录 | 激活后从随包完整清单建立当前发布；不需要另一步寻找 APK |
| F02 | A 的人工清单留存，安装 B 载体 | B 不会把 A 当自己的配对；人工文件不被覆盖或清理 |
| F03 | 安装／省略 optional、镜像滞后、`file:` 自更新 | 实测真实包管理器布局；缺失可诊断，不在 settled 后补写 profile |
| F04 | 外部 HTTPS／GitHub 发布源 | 手机候选及事务接续的 APK 地址均为宿主固定地址，不要求另改两端更新源 |
| F05 | web 直连、LAN 桥、自定义挂载路径 | 地址真实可达；不把手机导向回环，不信任伪造转发头 |
| F06 | 全新手机无请求头、无 Cookie 扫码 | 可匿名下载已验证 APK 并进入系统安装流程；不需要下载票据 |
| F07 | 无口令、错口令、正确口令、匿名 APK 并发及反代来源 | 控制接口 fail-closed；仅精确 APK 路由匿名；本机配置／图片入口不被远程代理借回环透传；控制登录限流不被下载重置或耗尽 |
| F08 | 固定 A 快照后发布 B，再下载／重连 A | APK 与本地主机 tgz 都取 A 的原字节或明确过期，不得到 B；手机不会静默跨快照拼接 |
| F09 | 跨 profile 先后替代、24 小时边界、重启、有效事务与 GC 竞争 | 各窗口完整且请求不刷新时钟；有效引用和响应不被清理；可信重新导入原发布可恢复原字节，匿名 GET 不能复活；人工区不受影响 |
| F10 | 硬链接后发布同语义版本测试 APK、跨文件系统、权限不足 | 载体原件不被反向修改；回退复制可靠；不移动原件、不原地覆盖共享 inode |
| F11 | 并发导入／发布／GC、崩溃及陈旧写者 | 无部分对象被服务；指针与引用按代际提交；锁无网络等待死锁 |
| F12 | A 更新 B，B 不健康回滚 A | 旧代码健康确认后当前入口切回 A；缺旧 APK 明确不可用；不宣传 B、不降级已装 App |
| F13 | 手机已有 A 的 appPending，另一更新失败并回滚 | 接续有明确成功证明或失败／取消／重查出口，不永久卡住 |
| F14 | 外发检查 off／失败，本地配对完整且健康 | 不出网仍能完成允许的本地 App 安装；不能由此触发外部插件更新 |
| F15 | 冻结、快照复用及离线恢复 | 相对“无载体基线”，`plugin-artifacts/` 与 `plugin-snapshots/` 的 `du` 增量 **≤ 5MB**；真正运行依赖仍完整；伪造标记不能绕过验证 |
| F16 | 错误载体版本、APK 哈希／大小／应用身份或签名 | 停在校验阶段；不服务错件，不把拉起安装器当完成 |
| F17 | +N 测试到正式版 | 公共 npm 无测试包；正式内部构建号可升级；清单 `app.version` **从 APK 实读**（`aapt dump badging` 的 versionName／versionCode）而非手填 |
| F18 | fork／上游／develop 不同内容 | 每组包、清单、HEAD、公开 tgz 和运行内容一致；不能复用已发布版本覆盖另一组字节 |
| F19 | 首装旧 App／不支持新联动的存量 App | 有可执行的首次迁移指引；不声称更新插件即可改写旧 App 自己构造的 GitHub 下载地址 |
| F20 | 匿名大文件并发及慢连接 | 控制／会话响应不因同步 72MB 哈希或无限下载并发阻塞；资源超限有可读失败 |
| F21 | 未配口令的存量安装升级 | 自动生成口令并可经 `qr-config`／二维码取得；控制接口 fail-closed；App 重扫一次后可继续；不写用户配置 |
| F22 | 人工区与托管区当前发布冲突 | 只认与运行内容标识一致且健康确认的那条；无命中则明确不可用，不退 latest |
| F23 | 遗弃 profile 的指针 | GC 先核 profile 存活性；遗弃指针写墓碑后释放引用，不永久占用 APK |

真机至少覆盖 F01、F04–F07、F08、F12–F14、F16–F19、F21 的关键用户路径。记录实际局域网耗时、签名与安装确认，不把“秒级完成”当任何网络环境下的保证。自动门禁仅使用隔离 HOME／profile／目录和假宿主；真实服务测试经授权串行执行。

## 7. 待验证假设与残余风险

1. **真实包管理布局**：主包经 registry、tgz、`file:` 安装均能取得正确载体；冻结恢复包排除载体后仍可独立运行。任何关键失败先阻止正式发布，不用事后 `pnpm add` 规避。
2. **npm 体积与政策**：72MB 级载体能否实际发布、下载，镜像延迟如何，仍需有授权的真实验证；Codex 先例和 dry-run 不构成保证。
3. **发布健康与分发就绪**：保持 healthy plugin 可降级运行，但明确两端联动尚未完成；不得用 settled 一个状态概括全部结果。
4. **存量 App 自举**：本次新流程要有最小 App 修复。未升级的旧 App 可能需先切主机源或从首装入口安装一次；兼容性与迁移路线需真机确认，不追认“旧 App 自动具备新逻辑”。
5. **硬链接与磁盘**：跨文件系统会复制；包管理器可能保留额外缓存。本设计只管理自身托管区，不承诺整机一份 APK，也不新增未确认的全机清理机制。
6. **保留上界**：24 小时与有效事务保护已确认；真正活跃的长事务可能延长占用。通过有效租约收敛遗留状态与资源诊断控制风险，不为了磁盘限额擅自破坏有效引用。
7. **宿主兼容**：不引入宿主版本门禁；用探测、显式诊断和新旧夹具保护行为，参见 [ADR 0017](<../../docs/adr/0017-host-compatibility-by-capability-probing.md>)。`dsh` 标记及枚举机制将来仍可能变化。
8. **应急运维**：文档说明从受信发布源／维护者取得同次发布 APK 与清单、离线核验并放入人工区的步骤；GitHub 不可达时不能只给同一条失败链接。备用文件源是人工预案，不自动增加网络下载器或来源轮询。
9. **匿名分发与策略迁移**：匿名仅公开安装包，不保护首装用户免受所有网络篡改；浏览器首装也没有“与本机已装 App 签名比较”的前提。生产网络应使用可信渠道／HTTPS 或人工核验；控制口令仍不得裸露在下载链接中。无口令控制被拒的行为变更须明确提示，不能悄悄让已有用户以为服务故障。

## 8. 明确不做与范围控制

- 不自动降级、卸载手机 App，不承诺系统静默安装。
- 不为 APK 下载增加票据或长期口令；不扩大匿名例外到清单、文件或控制前缀。
- 不由宿主按清单 App 地址从网络下载 APK，不对自身 APK 路由自取；外部清单和插件包仍按受信配置获取。
- 不给正式用户新增“不装载体”开关；省略 optional 视为有诊断的降级安装。
- 不移动、改写载体或 pnpm store，不自动清理人工区，不在事务完成后另写 profile 补装载体。
- 不把 App 修改扩展到日常业务功能，不把本机规则／工具和决策文档带进功能 PR。
- 不擅自改兼容范围、开 MR、bump 版本、改 develop 历史、推送、部署或重启。
- 本设计**已实施**：领域词汇与 ADR 0020／0021 记录在 develop，实施与验证见 GitLab #35。既有“未配口令即关闭认证”的默认行为在此次被明确修订为 fail-closed，须在迁移说明中向用户交代，不把它伪装成旧 ADR 已包含的事实。

# 适配上游 DSH 0.1.5-rc.2

状态：grill-with-docs 已完成最终确认，to-spec 已发布。

Spec：[GitHub Issue #7](https://github.com/marktrue-ahu/dsh-mobile-remote/issues/7)，标签 `ready-for-agent`。讨论记录见 [DSH 0.1.5-rc.2 适配需求讨论](../dsh-0.1.5-rc2-requirements-discussion.md)。

基线：从 `main` 切出 `feature/dsh-0.1.5-rc2-compat`。

## Problem Statement

使用者在电脑端把 DSH 升级到上游最新发行版 0.1.5-rc.2 之后，手机端的兼容性状态变得无法判断，而且部分能力会在没有任何提示的情况下失效。

具体表现为三件事。

第一，环境诊断给出的结论与实际不符。诊断会宣称已按新一代 Remote 协议工作，但手机收不到任何实时帧，问询与审批卡片也不再出现。使用者看到的是「一切正常」的诊断，却面对一个静默失效的功能，没有人能据此判断该升级什么、该等什么。

第二，手机上看到的排队消息与电脑端不一致。在电脑端改动队列、或内核认领了某条排队消息之后，手机端的队列视图不会即时更新，只能靠轮询兜底，使用者会看到已经执行过的消息仍然挂在待发送列表里。

第三，使用者无法判断自己手上的插件是否已经包含对新内核的适配。插件与 App 共享同一个版本号，而适配工作并不改变这个版本号，因此从界面上的版本信息看不出任何区别。

## Solution

把插件的受支持宿主收敛为上游当前已发布的 Typert 代际，并让「是否兼容」这件事变成使用者可以自己看见、也能自己正确处理的状态。

插件改为按能力探测来判定兼容性，而不是按版本号。它分别探测新一代 Remote 调用入口、Remote 事件桥入口、以及冷会话恢复入口这三项能力，任何一项缺失都让对应功能以明确的错误失败，并且在环境诊断里如实上报每一项的结果与原因。宿主版本号只用于展示与升级提示，不参与任何功能开关。

手机端的环境诊断新增一行电脑端兼容状态。使用者在这里能直接看到电脑端 DSH 版本、三项能力是否就绪、以及是否落在受支持范围内。当问询与审批能力缺失时，除了诊断之外，相关操作的失败提示会额外带上升级指引，因为那是唯一会让使用者彻底无法继续的场景。

队列视图改为订阅内核的会话内队列变更事件，让电脑端改动与内核认领都能即时反映到手机上，不再依赖轮询。

诊断中的代际结论不再由单个方法是否存在来推断。判定拆成三个互相独立的探测项，因为「能调用」与「能收事件」是两件独立成立的事，把它们合成一个布尔值会让半可用状态被误报为完全可用。

## User Stories

1. 作为手机端使用者，我想在环境诊断里看到电脑端 DSH 的确切版本，这样我能确认自己升级到了哪个内核。
2. 作为手机端使用者，我想在环境诊断里看到新代 Remote 调用能力是否就绪，这样我能判断模型目录与会话配置是否还能用。
3. 作为手机端使用者，我想在环境诊断里看到 Remote 事件桥是否就绪，这样我在看不到实时回复时能立刻知道原因。
4. 作为手机端使用者，我想在环境诊断里看到冷会话恢复是否就绪，这样我能判断对历史会话发消息是否会失败。
5. 作为手机端使用者，我想看到电脑端是否落在受支持范围内，这样我能判断自己该升级 DSH 还是该升级插件。
6. 作为手机端使用者，当某项能力缺失时，我想看到明确的原因说明，而不是一个含糊的失败提示。
7. 作为手机端使用者，当问询或审批能力缺失时，我想在操作失败的提示里直接看到升级指引，这样我不必自己去翻文档。
8. 作为手机端使用者，我想在电脑端改动排队消息后立刻在手机上看到变化，这样我不会重复发送已经排好的内容。
9. 作为手机端使用者，我想在内核认领了排队消息之后立刻看到它从列表消失，这样我不会以为它还等着执行。
10. 作为手机端使用者，我想让手机端的队列改动也即时反映到电脑端，这样两端看到的是同一份事实。
11. 作为手机端使用者，我想在电脑端内核版本过旧时仍然能正常使用其余功能，这样一次内核滞后不会让我整个手机端不可用。
12. 作为手机端使用者，我想在插件不兼容时得到一个明确的错误而不是安静的降级，这样我能立刻定位问题。
13. 作为手机端使用者，我想让实时回复、历史加载、发送消息这三条主链路在新内核上继续正常工作。
14. 作为手机端使用者，我想让问询与审批在新内核上继续保持手机与电脑双端同源，任意一端先答即两端同步收起。
15. 作为手机端使用者，我想让停止运行、会话分支、模型切换、归档这些操作在新内核上语义不变。
16. 作为手机端使用者，我想让上下文窗口与 token 用量在新内核上继续显示。
17. 作为维护者，我想让受支持的宿主范围在依赖声明里明确写出来，这样安装期就能发现不匹配而不必等到运行期。
18. 作为维护者，我想让代际判定的依据是能力而不是版本字符串，这样内核发布补丁版本时不会误报不兼容。
19. 作为维护者，我想在诊断里同时保留版本号与能力项，这样排障时既有身份信息也有行为信息。
20. 作为维护者，我想让不可达的旧代调用通道被清理掉，这样代码里不再需要维护永远不会执行的路径。
21. 作为维护者，我想让仍然为旧代宿主保留的交互通道带着显式弃用日志，这样旧代使用者不会被打断，同时会被明确提示升级。
22. 作为维护者，我想让验收范围如实标注在哪一代宿主、哪种形态、哪个平台上实测过，这样对外声明的兼容性始终有证据支撑。
23. 作为维护者，我想让未被验证的验收项显式记录为未验证，而不是留成空白，这样不会被误读为默认通过。
24. 作为维护者，我想让本次适配点即使不改变版本号也能被检索到，这样使用者与贡献者能确认自己拿到的插件包含适配。
25. 作为维护者，我想让「只支持当前代际」这条规则以架构决策记录的形式固化下来，这样未来内核换代时有一致的处理方式，而不是每次临时判断。

## Implementation Decisions

**受支持宿主范围**

受支持宿主收敛为上游当前已发布的 Typert 代际，依赖声明写为 `^0.1.5-rc.2` 形式，允许同代后续发行版。不再为更早代际提供适配保证。

**能力探测**

兼容性判定改用能力探测，并拆为三个互相独立的探测项：新代 Remote 调用入口、Remote 事件桥入口、冷会话恢复入口。三项分别上报，任一缺失使对应功能以明确错误失败。不把「能调用」与「能收事件」合并为单一布尔值，因为旧一代宿主恰好存在「有调用方法但没有事件流面」的组合，合并后会得到「宣称新代但事件桥未启动」的不一致结论。

**版本号的角色**

宿主版本号只用于诊断展示与升级提示，不参与功能门控。插件不拒绝加载在范围外的宿主；能力缺失由功能级明确错误与诊断上报承担。

**诊断契约**

环境诊断的响应新增一个宿主节，包含宿主版本号、三项能力布尔值、以及是否受支持。现有的服务探测与端点实测保持不变。

**旧代通道的处理**

仍然为旧代宿主保留的交互通道保持可用，并在其被启用时输出显式弃用日志，提示升级内核。用于旧代的一次性 Host Remote 调用封装、以及在内核端点表中不存在的调用映射，作为不可达路径删除。

**已知错误假设的修正**

发送请求的幂等标识改为无条件传递，不再以「是否检测到新代入口」为条件——新内核的请求参数校验是严格模式，缺少该字段会导致投递被直接拒绝，而不是仅失去幂等保护。会话标识的前缀剥离逻辑删除：新一代内核的会话标识不含该前缀，该剥离从未生效。内核在本次目标版本中新增了自己的请求幂等层，与插件自建的回执层并存，两者职责不同并各自保留：内核负责不重复执行同一请求，插件负责在传输层中断后回答「是否已送达」。

**队列视图的数据来源**

队列视图改为订阅内核的会话内队列变更事件，替代原先依赖新代事件桥转发队列帧的做法。该事件在上一代与当前代均存在且载荷一致，因此同一实现可覆盖当前受支持范围。

**验收范围与文档**

验收沿用既有的验收清单结构，宿主替换为本次目标版本，清除旧代宿主行，并补充本次新增项：升级提示、能力上报、队列帧同步、受支持范围判定。未被验证的项显式记录为未验证。

**版本号**

不改变插件与 App 的版本号，只把插件版本追平到已发布版本。版本号管理属于上游仓库作者，本 fork 不自行发版。本次适配点改为在变更日志中新增一个明确标注为本地的条目，以便检索。

**架构决策记录**

新增一条架构决策记录，记录「插件只支持当前内核代际」以及「以能力探测而非版本判断判定兼容」两项决定，并写明选择能力探测的理由与放弃旧代适配的代价。

## Testing Decisions

**唯一测试 seam：手机 HTTP 接口。**

所有行为断言都通过手机 HTTP 接口进行，包括新代宿主上的正常路径、能力缺失时的降级路径、队列帧同步、以及诊断中的宿主节。选择这一层的原因是验收清单已经把手机 HTTP 接口定为主要的自动化测试入口，本次不需要引入新的 seam。

**好测试的判据**：只断言通过接口可观察的外部行为——连接结果、错误码与错误语义、诊断字段、队列视图内容。不断言内部实现细节，例如不直接断言探测函数的返回值，而是断言诊断响应中对应的字段。

**被测试的模块**：插件侧的路由与能力探测行为、队列帧同步、诊断宿主节；App 侧的环境诊断展示。

**既有测试先例**：

- 插件行为的自动化入口见 `tools/e2e-check.mjs` 与 `tools/verify-rc1-*.mjs` 系列，均以手机 HTTP 接口为主要断言面
- 逐项验收清单见 `docs/rc1-acceptance-checklist.md` 的 T01–T19，本轮宿主替换为目标版本
- App 侧存在可用的单元测试套件，覆盖状态层与接口解析；环境诊断展示属于纯展示变更，不新增 seam
- 安装说明与兼容性文档需同步更新，见 `docs/09-compatibility.md` 与 `docs/06-install-run.md`

## Out of Scope

- Git 管理能力与其所在分支的合流，本次不讨论
- 上游仓库的版本号管理、发布与 GitHub Release
- 在范围外宿主上拒绝加载插件这类启动期硬拦截
- 改造上游未文档化的交互结算通道，使其不依赖宿主私有方法
- 上游未发布的其他代际宿主
- 对「完整兼容」的对外声明：本次完成后仍只标注在哪一代宿主、哪种形态、哪个平台上实测通过

## Further Notes

**已知的验收缺口与如实记录要求**。真实宿主上的问询与审批闭环、冷会话发送、图片链路三项在本次目标版本上仍属未验证，必须显式记录，不得沿用上一代宿主的既有证据平移作为本轮证据。文档中「不得对外宣称完整兼容」的结论在逐项验收完成前继续有效。

**版本号的可追溯性代价**。插件与 App 共享已发布版本号且本次不改变它，因此使用者无法从版本号区分「含适配」与「不含适配」的同版本插件。这一代价由变更日志中的本地条目与 commit 记录承担。

**本次评审中更正的既有事实**。仓库现有文档把「插件上下文隔离导致无法读取兄弟插件服务」记为设计原因，实际原因是服务激活时间点晚于插件装配，与隔离无关；上游官方插件指引也明确可选服务应当直接读取。该错误结论需要连带更正，因为后续维护者会继续据此推导出错误的实现方式。另有两处假设被证实不成立：把「存在 Remote 调用方法」当作代际标记，以及假设会话标识带前缀。

**同代内部差异仍需能力探测**。选择能力探测而非版本判断，是因为两个真实故障都发生在「版本一致但能力不同」的边界上：旧一代宿主存在 Remote 调用方法却没有事件流面；而 profile 的依赖副本可能比宿主更旧，使版本字符串不可全信。
